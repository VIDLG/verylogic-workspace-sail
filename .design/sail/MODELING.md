# Sail 工作区建模规范

这些规范用于让各 ISA 模型保持可执行、便于学习者阅读并具有一致的结构，同时避免把无关架构强行塞进同一种抽象。

本文件是当前生效的规范。

## 1. 标识符角色

| 角色 | 命名规范 | 示例 |
| --- | --- | --- |
| 类型、联合（union）、枚举（enum）、结构体（struct） | `lower_snake_case` | `word`、`instruction`、`rv32_decode_result` |
| 函数、参数、字段、普通值 | `lower_snake_case` | `decode_hack`、`old_pc`、`jump_control` |
| 构造器 | `UpperCamelCase`；当 ISA 规范助记符更清晰时保留其规范拼写 | `AInstruction`、`Decoded`、`ADDI`、`ECALL` |
| 常量 | 每个模块内部使用一种一致规范；规范定义的名称可以保留大写 | `RV32I_XLEN` |
| 架构寄存器 | 保留 ISA 可见的规范拼写 | Hack `A/D/PC/RAM`、RISC-V `X/PC` |

不要使用 C 风格的 `_t` 后缀。如果一个值会遮蔽类型名，或者两者在视觉上容易混淆，应按值的角色重命名，例如 `encoded`、`value`、`old_pc` 或 `target`。

## 2. 有类型的位字段

以下跨越重要边界的值应使用具名位向量类型：

- 完整指令字或数据字；
- 地址和程序计数器；
- 寄存器索引；
- 从解码阶段传给执行阶段的指令字段；
- 语义容易产生歧义的立即数、掩码、端口或 profile 数据字。

不要为每个只使用一次的局部位切片都创建类型别名。目标是显露架构含义，而不是让声明数量最大化。

## 3. 解码与编码

教学模型应同时明确展示编码关系与合法性：

1. 当合法编码构成小型、清晰的双射时，使用双向 Sail `mapping`；
2. 当指令类别、保留前缀或非法字段需要通过可读的 `match` 展示时，公开显式的 `decode_<isa>(encoded)` 入口；
3. 解码包装函数只有在确认编码合法后才能调用 mapping；
4. 成功路径返回有类型的已解码指令；非法/保留路径必须使用专用 typed Sail exception 或显式 result；
5. 当调用者没有合法恢复策略、只能中止当前 step 时优先 exception；当调用者需要恢复、继续分派或观察 fault 时使用 result；
6. 通过 mapping 暴露 `encode_<isa>(instruction)`；如果 ISA 太复杂，无法用一个清晰的双射表达，则定义独立编码器。

Hack 展示 `mapping encdec` 加负责合法性检查的 `decode_hack` 包装函数。RV32I 的 opcode、`funct3`、`funct7` 和保留字段检查更加复杂，因此使用独立、显式的解码和编码函数。

规范的编码/解码往返测试很有价值，但固定已知机器字必须继续作为独立测试判据。


## 4. 程序镜像、取指与生成驱动

即使教学程序被嵌入生成的 Sail，也要让执行路径保持清晰分层：

1. 生成驱动将原始编码字或字节装入模型自己的指令存储；
2. ISA 模型从该存储中取出原始指令字或指令记录；
3. 当 ISA 存在独立解码阶段时，由 ISA 解码器将原始编码转换成有类型的指令；
4. 执行阶段只消费有类型的指令；
5. 一个由模型拥有的 step 函数组合取指、解码和执行；正常路径可直接返回 `unit`，不可恢复错误可抛出 typed exception，需要调用者分派的架构 outcome 则显式返回。

生成驱动不得嵌入已解码的指令构造器，也不得把地址查找与 `decode_<isa>` 合并。逐机器字的源码标注应放在原始镜像加载语句上，让注释描述来源关系（provenance），但不成为语义。

必须尊重每台机器自己的内存组织：

- Hack 这类哈佛结构机器拥有分离的程序 `ROM` 和数据 `RAM`；生成驱动初始化 `ROM`，`fetch_hack` 从中读取，指令执行永远不能写入它；
- RV32I、Pancake、SUBLEQ 这类统一内存机器将镜像装入普通内存，因此取指必须观察执行过程可能修改的同一批字节或机器字；
- 特殊指令记录保持架构局部：SUBLEQ 取出三个原始地址字节，不为它虚构 opcode 解码器。

生成驱动是测试平台，而不是 ISA 模型的一部分：

- 可以负责复位和装载编排、基于 metadata 的完成判定或伪 HALT 检测、watchdog、源码断言和宿主输出；
- 必须区分架构 halt/trap 结果与循环停止策略；step budget 可以停止驱动，但这不代表 ISA 成功完成；
- 普通 executor run 必须具有有限 watchdog；默认模式或 watchdog 模式耗尽应视为失败；有界完成必须由用户显式请求，并配有可观察断言；
- 同时支持源码 directive 与 CLI flag 的运行时设置统一遵循 `CLI > source > default`；生效的覆盖值必须在重新加载前序列化进生成制品，驱动生成过程不得消费制品之外的隐藏状态；
- 微妙的循环进入条件应集中在一个命名清晰的驱动辅助函数中，并在循环结束后验证真实停止原因；
- 只有真实编码的 halt/trap 才属于模型；ROM 末尾策略、降低后的自循环 metadata 和 `max_steps` 留在驱动；
- 上述驱动职责不得取代模型自己的取指、解码和执行路径。


## 5. 教学源码指令项与带注释制品

### 5.1 共享指令项契约

所有 ISA 包共享一套小型教学源码契约，同时保留各 ISA 自己的目标和值语义：

- `.description <text>` 为配套课程提供稳定、面向人的标识，并持久化进生成制品；
- `.max_steps <positive integer>` 配置有限的执行器 watchdog，但不发射指令；
- `.assert <target> == <integer>` 和 `!=` 比较目标的精确位模式；
- 有序比较必须显式使用 `signed(<target>)` 或 `unsigned(<target>)`；
- 等值断言不得使用 signed/unsigned 包装器。

共享解析器负责表层语法、整数语法、重复的单例指令项和比较模式拼写。每个 ISA 自己负责目标规范化、别名、位宽、范围、对齐和生成的 Sail 表达式。

受约束 C 等前端可以在源码注释中携带相同指令项。每一行带标记的指令项都必须立即解析；格式错误或未知的指令项必须失败，不能静默消失；生成的教学汇编必须保留诊断使用的原始源码行号。

### 5.2 带注释的机器镜像

生成的带注释机器镜像以且仅以一个连续、带版本的 `//%` manifest block 开始。公共外层结构记录：

- schema/version；
- ISA/profile；
- 稳定的源码标识；
- description 和 comment level；
- 已解析的运行时设置及其来源；
- 规范断言及其源码显示拼写；
- 可选但非空的前端来源信息；
- completion metadata；
- ISA metadata。

公开外层结构不包含 executor metadata 字段。

线格式是仓库定义的规范受限 S-expression，不是可执行 Lisp，也不是 JSON：

- 顶层恰好是一个形式正确的 `(artifact ...)` 列表；
- 只允许符号、UTF-8 引号字符串、十进制整数和形式正确的列表；
- 拒绝浮点数、quote/quasiquote 形式、dotted pair、vector/bracket、keyword、reader boolean、保留的 `nil`/`t`、重复或未知字段，以及非规范格式；
- 通用嵌套值使用显式 `(object ...)`、`(array ...)`、`none`、`true` 和 `false`；
- 断言使用声明式比较 AST，例如 `(assert (<= (signed R6) -5) (source-line 68))`。

`sexpdata` 只作为有边界的词法切分器和解析器。仓库代码必须自行执行子集、语法、单一顶层形式、深度/节点数量限制，以及“解析后重新渲染”的规范等价性检查。

持久化的公共与 ISA 专属结构使用严格、冻结、禁止额外字段的 Pydantic v2 模型：

- validator 负责局部字段不变量；
- profile 闭包、目标规范化、地址对齐和 completion word 绑定等依赖机器上下文的检查留在 ISA artifact codec。

渲染规则：

- `summary` 和 `full`：一个带缩进的形式跨多行连续输出，每行都以 `//% ` 开头；
- `none`：同一个形式紧凑输出为单行，并保留 `//% ` 前缀；
- `summary` 和 `full` 的人类可读前言必须从同一个已验证模型派生；
- `none` 只保留机器可读的 manifest block。

带注释制品的加载器必须严格。原始或外部机器码格式需要各自显式命名的前端，不能通过宽松回退为其虚构执行 metadata。

### 5.3 线格式契约与运行时设置

线格式契约与具体库无关：Python 当前使用 `sexpdata`，未来 Rust 实现可以使用 `lexpr`/`serde-lexpr`；任何库更宽泛的方言都不能重新定义仓库子集或规范拼写。

运行时设置遵循 `CLI > source > default`。写入机器镜像前完成解析，将具体值和来源序列化，严格重新加载文件，然后只从重新加载后的契约生成驱动。禁止把覆盖值作为隐藏的 Python 状态传给驱动生成过程。

### 5.4 信息分层与共享基础设施

信息应保留在最有用的层次：

- 源码：意图、标签、别名、伪指令、源码指令项和可选 C 行来源；
- 教学汇编：规范化的目标汇编，同时保留有用别名和伪指令来源链；
- 机器镜像：全局 manifest，加上由 comment level 决定的逐机器字 source/canonical/bits 来源；
- 生成驱动：同一全局标识与运行时契约，以及原始镜像加载、循环策略、断言和诊断输出；
- ISA 模型：只包含架构状态、取指/解码/执行/单步、合法性和提交行为。

`tools/isa_support` 下的共享 Python 基础设施负责源码指令项语法、Pydantic manifest 模型、规范受限 S-expression 的解析和渲染、进程执行、宿主 C 编译，以及支持回滚的制品发布。

ISA 包可以依赖该基础设施，但共享包永远不能导入某个 ISA。规范 API 应从其定义子模块直接导入；没有真实的带版本使用方时，不得添加兼容别名或宽泛 facade re-export。共享机制，不共享汇编器语义或驱动策略。


## 6. 非法编码与保留编码

- 通配/default 解码分支可以抛出专用 typed exception，或返回 `DecodeIllegal`、`Reserved` 等显式结果，但绝不能构造一条合法指令；
- Sail 没有内置 exception 类型；使用 exception 时必须声明项目自己的 `union exception`，constructor 应准确表达错误并在有助于诊断时携带原始机器字；
- 只有成功解码的指令才能执行；decode 必须在任何架构状态写入前完成，throw/result 路径都不得部分更新架构状态；
- 当错误对当前 step 不可恢复、调用者唯一合理动作是失败时，优先让正常 API 直接返回 `instruction`/`unit` 并在错误路径 throw；当 fault 是可观察架构 outcome、调用者需要恢复或多级 decoder 需要继续分派时，使用显式 result/outcome；
- 如果某个 ISA profile 不存在非法机器编码空间，应记录这一事实，而不是虚构失败分支。SUBLEQ 取出的 A/B/C 字节记录就属于这种情况。

## 7. 架构局部设计

应共享规范和基础设施，而不是偶然相似的架构结构。每个 ISA 自己拥有：

- 架构状态；
- 解码契约；
- 执行结果；
- 汇编语法、降低和编码；
- 制品专属验证；
- 生成驱动模板和完成策略；
- 工作流阶段；
- 测试。

公共源码指令项、manifest 基元、发布流程和宿主构建机制留在工作区基础设施。`XLEN`、`IALIGN`、指令助记符和架构寄存器名等官方术语应保持可识别。

扩展 ISA 时必须同步：

- 模型与直接 Sail 一致性测试；
- 受模型 API 变化影响的生成驱动模板；
- 包 README 与中英文文档；
- ISA 自己的 `.design` 计划；其中只记录架构专属决策，并链接本文件中的共享规范。

## 8. 设备契约与平台组合

可移植设备契约必须同时与 ISA 核心和目标专属传输方式分离：

1. 共享契约可以定义逻辑画面、输入动作、帧边界、seed、退出、故障和可观察事件；
2. 每个具名目标平台绑定自己决定这些语义使用 MMIO、架构端口、内建地址、保留内存还是显式模型事件；
3. 共享设备语义不意味着共享物理地址、总线时序、指令形式、字节布局或中断行为；
4. 无设备 ISA profile 必须继续保持无设备；Pancake 或 SIC-1 SUBLEQ 这类具有架构 I/O 的 ISA 必须保留其原始 I/O 语义；
5. 应用设备位于具名 Sail 平台组合中，并通过未改变、由模型拥有的 ISA step 函数推进机器；
6. 宿主适配器可以注入输入快照、提取规范画面并报告事件，但不得执行指令、游戏逻辑或绘图语义；
7. 缺少可移植平台所需内存或 I/O 能力的 profile 必须显式拒绝，不能接受隐藏的宿主协助；
8. 更大或具有设备能力的变体必须成为新的具名 profile/composition，并拥有自己的制品标识、测试和文档；不得静默修改兼容基线。

只有出现真实的多目标使用方后，才共享语义契约和宿主 ABI。每个目标绑定必须保持足够局部，让 Hack MMIO、RV32I MMIO、Pancake 端口和 SUBLEQ 内建地址仍然清晰可辨、便于教学。
